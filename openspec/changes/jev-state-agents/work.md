# 진행과 검증 기록

## 2026-11-15 설계 제안

- 경위
  - [KorCCVi 수법 분석](../../../docs/analysis/korccvi-scam-tactics.md)으로 R1~R9와 NEW 수법을 대화 특징 6개(F1~F6)로 다시 묶었다.
  - 사용자는 다음 방향을 제시했다.
    - 이 6개를 Jev가 판단하는 상태로 만든다.
    - 관찰·주의·경고 단계는 쓰지 않는다.
    - 켜진 상태에 맞는 에이전트를 부른다.
    - 대응은 전역 문구가 아니라 LLM이 지금 대화를 보고 최종 판단해 쓴다.
  - 이 방향에 다음 두 가지를 더해 [spec](spec.md)과 [design](design.md)에 제안으로 기록했다.
    - 절대선: LLM이 정상으로 판단할 수 없는 요구
    - 판단 근거 제한: 상대가 주장한 신분·절차는 근거로 쓰지 않는다
- 데이터 근거(KorCCVi 사기 694통화, 판단불가 제외, LLM 라벨, 사람 검수 없음)
  - 상태별 출현율(괄호는 첫 등장 상대 위치 중앙값)
    - F1 20.5% (0.28)
    - F2 35.3% (0.30)
    - F3 18.4% (0.53)
    - F4 79.0% (0.20)
    - F5 39.5% (0.37)
    - F6 83.0% (0.03). F2·F4·F6는 2026-11-16 묶음 수정 후 값이다.
  - 특징이 2개 이상인 통화는 608건(88%)이다.
  - 이 수치는 기존 라벨을 F 묶음에 다시 배정해 낸 것이다. 재배정 스크립트는 아직 저장소에 없고, 대화 중 임시로 실행했다.
- 아직 실행하지 않은 것
  - 코드 변경
  - Jev 실제 호출
  - 평가

## 2026-11-16 팀장 협의와 이슈 등록

- 사용자가 팀장과 이 구조로 전환하기로 협의했다. 상태별 LLM은 Claude API 에이전트로 쓰고, 판단 결과별 점수를 매긴다.
- F1은 복잡하지 않게 하기로 했다. LLM 호출 1번과 사기계좌 조회 tool 하나, 확인 질문 3개로 구성한다([design](design.md)의 F1 간단 구성).
- 작업 이슈 [#13](https://github.com/M4-Scamshield/scam-agent/issues/13)을 등록했다.
- 코드 변경, Jev 실제 호출, 평가는 아직 하지 않았다.

## 2026-11-16 미정 사항 결정

- 사용자가 [design](design.md#결정-사항-2026-11-16-사용자-결정)의 결정 사항을 정했다.
  - `voice_phishing` 질문은 당분간 남기되 나중에 없앤다. 없애는 근거를 얻으려고 평가에서 "이 질문만 Yes인 사기"를 따로 센다.
  - 상태 에이전트만 Claude API로 만든다. BE 계약은 바꾸지 않고 상태 결과를 `OBSERVE/WARN`과 score로 바꿔 내보낸다.
  - 점수는 임시 값으로 시작한다. tool은 F1·F3용 Mock만 만든다.
- 남은 미정: Jev 기준값, 실제 tool API, F2 기준표

## 2026-11-16 Jev 상태 질문 소량 실호출

- 스크립트: [probe_states.py](../../../experiments/jev_states/probe_states.py)
  - 질문: 공통 지시 + 상태별 Yes/No 기준, 그리고 기존 `voice_phishing`
  - 결과: [probe.json](../../../experiments/jev_states/results/probe.json). call_id, 정답, 판단·확률, 지연, 토큰만 있고 대본은 없다.
- 표본: KorCCVi 사기 15통화(판단불가 제외, 3,000자 이하, seed 0, F1·F2·F3·F5 양성 우선 포함)와 정상 5통화
  - 통화마다 전체 대본(화자 표시 줄 목록)을 1번 보냈다.
  - 정답은 LLM 라벨을 F로 다시 묶은 통화 단위 존재 여부다. 사람 검수는 하지 않았다.
- **형식 확인:** 질문 7개를 한 요청에 보내도 받는다. 20/20 성공, 실패 0이다. 각 답에 `choice`와 Yes/No 확률이 온다.
- **지연·토큰:** 지연 중앙값 0.23초, 최대 4.23초. 입력 토큰 중앙값 3,307, 합계 71,635. 출력 토큰 합계 4,160.
- **기본 판단(Yes) 결과** (사기 15통화 안에서 정답 대비, 정상은 5통화)

  | 질문 | 재현 | 사기 통화 오탐 | 정상 통화 Yes | P(Yes) 중앙값(정답 있음/없음) |
  |---|---:|---:|---:|---|
  | F1 | 2/3 | 0/12 | 1/5 | 0.98 / 0.00 |
  | F2 | 3/5 | 2/10 | 0/5 | 0.84 / 0.03 |
  | F3 | 3/3 | 1/12 | 2/5 | 0.85 / 0.05 |
  | F4 | 7/10 | 1/5 | 0/5 | 0.62 / 0.04 |
  | F5 | 2/7 | 0/8 | 0/5 | 0.14 / 0.00 |
  | F6 | 8/13 | 0/2 | 0/5 | 0.67 / 0.00 |
  | voice_phishing | 10/15 | — | 0/5 | 0.73 / 0.00 |

- **해석**
  - 사기 통화에서 F 중 하나라도 Yes인 통화는 13/15이고, `voice_phishing` Yes는 10/15였다. 작은 표본이지만 상태 질문이 더 많이 잡았다.
  - `voice_phishing`만 Yes인 통화는 0건이었다. 없앨 근거 쪽으로 기운다. 큰 표본에서 다시 센다.
  - 정상 2통화에서 F1·F3이 Yes였다. 상태는 사기 판정이 아니므로 설계대로 에이전트가 걸러야 할 경우다. 정상 통화의 종류는 이번에 확인하지 않았다.
  - F5(2/7)와 F6(8/13)가 약하다. 기준값을 0.1까지 낮춰도 F5 4/7, F6 9/13이다. 기준값보다 질문 문구 문제로 본다.
  - F2·F3은 기준값을 0.3으로 낮추면 오탐이 F2 5/15, F3 7/17로 빠르게 는다. 기준값은 상태마다 따로 정해야 한다.
  - 사기 2통화(4줄, 10줄)는 모든 질문이 No였다. 짧은 통화라 근거가 적었을 수 있다.
- **한계:** 20통화뿐이다. 통화 전체 대본을 한 번 보냈으므로 발화 시점별 감지와 지연은 재지 않았다. 정답은 사람 검수 전 LLM 라벨이다.

### F5·F6 문구 수정 (v2)

- v1에서 놓친 원인을 정답 라벨로 확인했다. 모델 오류보다 정의 차이였다.
  - F6를 놓친 5건 중 4건은 대출빙자 통화의 금융회사 자기소개(R8)였다. v1 질문은 "소속만 밝히면 No"였다.
  - F6를 놓친 나머지 1건은 N2로 묶였지만 실제로는 "고액 일당" 제시였다. [group_new.py](../../../experiments/korccvi_tactics/group_new.py)의 N2 규칙에서 `일당`(범죄 무리)이 급여 뜻의 "일당"에도 걸린 오분류다.
  - F5 미탐은 대부분 N7(안심·의심 무마)과 N9(할 말 지시)였는데, v1 질문에는 둘 다 없었다.
- v2: F5에 의심 무마와 할 말 지시, 주변 차단을 넣었다. F6에 기관·회사 자기소개, 규정·공문, 정부 지원 상품 내세움을 넣었다. 같은 20통화로 다시 돌렸다. 결과는 [probe_v2.json](../../../experiments/jev_states/results/probe_v2.json)이고 실패는 0이다.

  | 질문 | v1 재현 | v2 재현 | v2 사기 통화 오탐 | v2 정상 Yes |
  |---|---:|---:|---:|---:|
  | F5 | 2/7 | 5/7 | 1/8 | 0/5 |
  | F6 | 8/13 | 12/13 | 0/2 | 0/5 |

- F1~F6 중 하나라도 Yes인 사기 통화가 13/15에서 15/15로 늘었다. 정상 통화 중 하나라도 Yes인 통화는 2/5로 그대로다(F1·F3).
- v2에서 F6의 남은 미탐 1건은 위 N2 오분류 통화다. F5의 남은 미탐 2건은 의심 무마 사례다.
- 문구를 바꾸지 않은 질문도 결과가 조금 달랐다. F2 사기 통화 오탐은 2에서 3, F3은 1에서 0, `voice_phishing`은 10/15에서 9/15다. Jev 응답에 실행마다 변동이 있다. 기준값은 반복 실행이나 큰 표본으로 정한다.
- 정상 5통화의 종류는 확인하지 않았다. F6를 넓혔으므로 금융 상담 같은 정상 통화에서 오탐이 늘 수 있다.

### 묶음 수정과 경계 정의 (v3)

- 사용자 결정(2026-11-16)에 따라 다음을 반영했다.
  - **묶음 수정**
    - N2 규칙을 `범 일당|일당 규모`로 좁혔다.
    - 이득 약속 라벨 6개를 `OVERRIDES`로 N6에 넣었다.
    - 수정 전후 1,605개 라벨을 대조했고, 바뀐 것은 이 6개뿐이다.
  - **정의**
    - F2: 계좌 개설 여부 추궁은 No(F4)
    - F4: 선입금 없는 저금리·대출 제안은 No
    - F5: 단순 해명·안심은 No
  - spec 표와 질문 문구에 반영했다. 평가 정답에서 F5는 N7을 빼고 센다.
- v2와 같은 20통화로 v3를 실행했다(`--same-as`). 결과는 [probe_v3.json](../../../experiments/jev_states/results/probe_v3.json)이고 실패는 0이다. 아래 표는 v2와 v3 모두 수정된 정답으로 다시 채점했다.

  | 상태 | 정답 수 | v2 재현 | v3 재현 | v2 사기 FP | v3 사기 FP | v3 정상 Yes |
  |---|---:|---:|---:|---:|---:|---:|
  | F1 | 3 | 2/3 | 2/3 | 0/12 | 0/12 | 0/5 |
  | F2 | 4 | 3/4 | 3/4 | 3/11 | 0/11 | 0/5 |
  | F3 | 3 | 3/3 | 3/3 | 0/12 | 0/12 | 2/5 |
  | F4 | 12 | 8/12 | 7/12 | 0/3 | 0/3 | 0/5 |
  | F5 | 4 | 4/4 | 4/4 | 2/11 | 1/11 | 0/5 |
  | F6 | 12 | 12/12 | 12/12 | 0/3 | 0/3 | 0/5 |

- **v3에 남은 미탐·오탐**
  - F1 FN 1: v2와 같은 5줄 조각(경계)
  - F2 FN 1: 생년월일 본인 확인. 정답의 R3(약한 신호)가 spec No와 겹친다.
  - F3 FP 2: 정상 상담의 반송·문의처 안내. 에이전트가 거를 경우다.
  - F4 FN 5
    - 4건은 선입금 없는 저금리·대출 제안이다. 정의대로 No이고, 정답의 N6이 이런 제안까지 F4로 센다.
    - **Jev 미탐은 연루 통보 1건(0.46)이다.** spec 정의 기준으로는 F4 재현 7/8이다.
  - F5 FP 1(0.50): "조회 기록이 남지 않는다"며 안심시킨 통화. 확인을 막는 말과 안심시키는 말의 경계다.
- F2의 계좌 개설 추궁 오탐 3건이 사라졌다. F1의 정상 반송 오탐도 이번에는 없었다. 다만 Jev 결과는 실행마다 변동이 있다.
- 사기 통화 중 상태가 하나라도 켜진 통화는 15/15다. `voice_phishing`은 9/15이고, 이 질문만 Yes인 통화는 0이다.
- 한계: 같은 20통화로 문구를 고친 결과다. 표본에 맞춘 조정일 수 있으므로 다른 통화로 확인해야 한다.

### v4 정상 오탐 대사 단위 확인 (2026-11-19)

- 상태가 켜진 정상 50통화를 대사를 쌓아 1,012번 다시 보냈다(사용자 결정, 입력 약 381만 토큰, 실패 0). 스크립트는 [prefix_states.py](../../../experiments/jev_states/prefix_states.py)이고, 줄 단위 평가 하네스의 첫 형태로 쓴다.

### 상태 단독 출현과 라우팅 결정 (2026-11-19)

- 정상 F3·F6 오탐을 Jev 질문으로 줄이는 대신, Jev는 행동 감지만 하고 Haiku가 맥락으로 거르기로 했다(사용자 결정). 직전에 제안한 "F3·F6만 켜지면 에이전트를 부르지 않음"과 "F3·F6 정의 좁힘"은 쓰지 않는다. 정상 데이터가 콜센터 상담뿐이라 친구 사이 송금·링크 공유 같은 일상 행동은 재지 못했으므로, 어느 상태도 Jev 단독으로 경고하지 않는다.
- KorCCVi 694통화(현재 평가 정답 규칙)에서 특징이 하나뿐인 통화는 129건이다. F6 88, F4 22, F1 10, F2 6, F5 2, F3 1건이다. 상태 하나만 켜져도 LLM을 부른다.
- F3·F5는 단독 사기가 각 1%라, 이 통화에서 F3·F5만 켜진 동안은 LLM을 부르지 않고 보류한다. 다른 상태가 켜지면 보류한 F3·F5도 판단한다(사용자 결정). 규칙은 [spec](spec.md), 이유와 남은 위험은 [design](design.md#결정-사항-2026-11-19-사용자-결정)에 있다.
- 수치는 [KorCCVi 분석](../../../docs/analysis/korccvi-scam-tactics.md#행동-특징-f1f6으로-다시-묶기)에 있다.

### 최근 대사 창 방식 비교 (2026-11-22)

- 사용자 제안: 상태가 켜졌는지는 State가 기억하므로, Jev는 대화를 계속 쌓지 않고 지금 대사에 행동이 나왔는지만 보면 된다. 대화 길이를 늘려도 입력은 약 3.5k→4.7k 토큰, 지연은 0.22→0.24초라 비용보다 정확도로 정하기로 했다.
- 마지막 대사와 앞 4줄만 보내는 v5 후보를 사기 40, 정상 오탐 20통화로 재 봤다(1,459요청, 실패 0, 약 543만 토큰). 스크립트는 [window_states.py](../../../experiments/jev_states/window_states.py), 대사 단위 채점은 [score_lines.py](../../../experiments/jev_states/score_lines.py)이고 이것이 줄 단위 평가 하네스다.
- 통화 단위 재현은 전체 1회 판단과 같거나 높았고(F3만 1통화 적음), 첫 감지는 라벨 대사와 같은 줄이었다. 정상 통화의 F3·F6 Yes 대사는 누적 방식의 약 1/4이다.
- Yes가 난 대사마다 상태 LLM을 부르면 통화당 사기 15.6회, 정상 1.4회다. 창 방식을 채택하려면 반복 호출 규칙을 정해야 한다. 표와 해석은 [버전별 변경 이력](../../../docs/analysis/jev-state-question-versions.md#v5-후보--최근-5줄-창-2026-11-22)에 있다.
- 같은 날 사용자가 창 방식을 채택했다. spec의 Jev 입력과 질문을 바꿨고, 구현할 수 없던 "근거 발화가 바뀌면 다시 부른다" 규칙은 빼고 재호출 규칙을 미정으로 옮겼다([design](design.md#결정-사항-2026-11-22-사용자-결정)).

### 멘토링 지적: 기존 점수 (2026-11-22)

- 기존 2AS(`voice_phishing` 한 질문)는 정확도가 낮고 점수가 49점까지 오르면 내려가지 않는다는 지적을 받았다. 사용자는 대화가 정상으로 돌아가면 점수도 내려가야 한다는 뜻으로 이해했다.
- 원인: BE `agent-bridge`가 점수를 Jev 확률 × 100으로 만들고, Jev가 No면 Gemini를 부르지 않는다. 40~49점은 Jev가 No지만 애매한 경우라 검증 없이 SUSPECT에 머문다. 대화가 쌓여 같은 내용이 계속 들어가니 확률도 그대로다. 개발용 200통화에서 사기 28/120이 50점 미만이었고 그중 11통화가 40~49점이었다. 이 28통화 모두 상태 질문은 하나 이상 켜졌다.
- 새 설계의 점수는 상태 LLM 판단을 더하는 방식이라 이 지적("내려가지 않음")은 그대로 남는다. 점수를 언제 내릴지는 아직 정하지 않았다(사용자가 이번에는 건너뛰기로 함). risky 근거를 내리면 사기범이 요구 뒤 평범하게 말할 때 위험이 낮아지는 문제가 있다. 점수 변환은 팀원 BE 코드라 계약을 바꾸려면 협의가 필요하다.
- 같은 날 아래 "판단·점수 규칙 결정"에서 점수를 언제 내릴지 정했다.

### 판단·점수 규칙 결정 (2026-11-22)

사용자와 판단 흐름 전체(Haiku 판단, tool, 코드 보정, 점수, 알림, BE 출력)를 정리했다. 결정한 것은 [design 결정 사항](design.md#결정-사항-2026-11-22-사용자-결정)과 [spec](spec.md#충족해야-할-동작)에, 아직 제안인 것은 [design 미정 사항](design.md#미정-사항)에 있다.

- 결정
  - 재호출: `risky`면 다시 부르지 않는다. `uncertain`·`within_normal`은 같은 상태가 다시 Yes면 다시 부른다.
  - SUSPECT·WARN 두 단계 대신 통화 상태(위험·주의·정상)를 쓴다. 알림은 위험일 때만 띄운다.
  - 점수는 상태별 칸의 합이다. `risky`는 고정한다. `uncertain`은 1분마다 절반으로 줄인다.
  - BE가 새 줄을 여러 개 합쳐 보내면 새 줄마다 Jev 창을 만든다. 같은 날 측정 뒤 새 줄 전부를 한 번에 묻는 방식으로 바꿨다([아래](#새-줄-묶음-확인-2026-11-22)).
- 처음 제안을 바꾼 것
  - 처음에는 시간에 따른 감소에 반대했다. 사기범이 조용한 구간을 만들기 때문이다. 하지만 `risky`를 고정하고 알림을 `risky`로 띄우면, `uncertain`을 줄여도 놓치는 알림이 없다. 그래서 `uncertain`만 줄이기로 했다.
  - `uncertain` 뒤 10대사가 지나면 Haiku를 다시 부르는 안도 있었지만, 호출이 늘어서 시간 감소로 대신했다.
- BE 코드 확인(팀원 저장소, 읽기만 함)
  - 발화 한 줄은 리턴제로 STT의 `final` 구간 하나다(`RtzrSttClient`). 문장 단위가 아니고, 실제 한 줄 길이는 재지 않았다.
  - 실행 대기 중인 작업이 있으면 새 발화를 그 작업에 합친다(`IntakeService`). 그래서 agent 호출 한 번에 새 줄이 여러 개일 수 있다.
  - `agent-bridge`는 그중 마지막 줄만 새 대사로 `run_turn`에 넘긴다. 창 방식에서 가운데 줄의 행동을 놓칠 수 있는 이유다.
  - 가짜 STT는 음성 3초마다 대본 한 줄을 만든다.
  - 발화 시각이 agent 요청에 들어가는지는 확인하지 못했다.
- KorCCVi 집계
  - 한 줄은 공백을 빼고 중앙값 33자(사기 706, 정상 711통화)다. 말하는 속도로 어림하면 약 5~6초이고, 10대사는 약 1분이다.
  - 통화 길이는 중앙값 15줄이다.
  - 그래서 처음에는 KorCCVi 평가에서 1줄을 5초로 보려 했다. 실제로는 KorCCVi 대사마다 시작 시각(`start`)이 있어 Haiku 실험은 그 시각으로 감소를 쟀다. 대사 간격 중앙값은 정상 6.6초, 사기 6.3초다.

### Haiku 상태 판단 검증 (2026-11-22)

창 방식 측정에 쓴 60통화(사기 40, 상태가 켜진 정상 20)에 정한 라우팅·재호출·점수 규칙을 그대로 적용하고, 상태가 켜질 때마다 Haiku에 전체 대화를 보내 판단을 받았다. 스크립트는 [haiku_states.py](../../../experiments/jev_states/haiku_states.py), 결과(판단·근거 줄 번호만, 원문·이유 없음)는 `experiments/jev_states/results/haiku55low_window5_dev200.json`이다. Haiku의 이유·대응 문구는 대본을 인용할 수 있어 저장소 밖에만 저장했다.

- 설정: `claude-haiku-5-5`, effort `low`. 요청 228건, 오류 0, 입력 약 40만·출력 약 11만 토큰.
- 사기 40통화
  - 위험(알림) 36/40, 나머지 4는 주의로 끝났다. 예전 `voice_phishing` 전체 대본 1회 점수 40 이상은 34/40, 70 이상은 20/40이다.
  - 첫 정답 대사에서 첫 알림까지 중앙값 2줄·9초, 최대 21줄.
  - 처음 `risky`가 된 상태: F6 17, F4 11, F5 5, F1 2, F2 1.
  - Haiku 요청은 통화당 평균 5.0, 최대 17.
- 정상 20통화
  - 위험 1/20, 주의로 끝남 3, 정상 16. 통화 시간 중 위험·주의 비율 평균 23%이고, 대부분 첫 줄 기관 소개에 켜진 F6 `uncertain`이다.
  - 위험 1건은 교재 재구매 안내에서 자녀 개인정보를 모으고 기한을 거는 통화로, F4 `risky`다. 라벨은 정상이지만 행동은 경계할 만하다.
- 놓친 사기 4통화
  - 수사기관 사칭 짧은 통화 2건(3~4줄): F6만 켜졌고 돈·정보 요구 전이라 `uncertain`. 한 통화는 사건 연루 언급이 있었지만 Jev F4가 켜지지 않았다.
  - 대출 상담형 2건: 돈·정보 요구가 끝까지 나오지 않았다. 한 통화는 Haiku가 F1·F2·F3를 대출 목적에 맞는 요구로 보고 `within_normal`로 판단했고, 상대가 말한 은행 지점을 공식 지점으로 받아들였다. 신분 주장을 근거로 쓰지 말라는 판단 제한과 어긋난다.
- 그 밖
  - Haiku가 절대선 `true`를 준 판단은 11건이었고 모두 이미 `risky`여서 고친 판단은 0이다. 절대선이 없는 F4·F6에도 `true`를 준 경우가 있어, 코드는 절대선이 있는 상태에서만 이 값을 봐야 한다.
  - 사기 통화에서 상대가 읽어 준 주민번호를 확인만 시킨 경우를 F2 `within_normal`로 본 판단이 있다. 정보 방향 판단이 맞는지는 검수가 필요하다.
- 남은 검토: 짧은 수사기관 사칭을 `uncertain`으로 둘지, 신분 주장 근거 사용을 프롬프트에서 더 막을지, 정상 통화 주의 시간(23%)을 줄일지(F6 첫 `uncertain` 점수·감소 조정).

### 새 줄 묶음 확인 (2026-11-22)

사용자가 새 줄마다 묻지 말고 새 대사들 중에 행동이 있는지 한 번에 묻자고 제안했다. 작게 재 보고 잘되면 그렇게 가기로 했다(사용자 결정).

- 방법: 창 방식 60통화 중 사기 8·정상 4통화(seed 0)를 3줄씩 묶어, 새 3줄과 앞 4줄을 보내고 "마지막 3줄 중 행동이 있나"를 물었다([chunk_states.py](../../../experiments/jev_states/chunk_states.py)). 같은 통화의 줄마다 창 결과에서 묶음 안 한 줄이라도 Yes면 Yes로 보고 비교했다. 67요청, 실패 0.
- 결과: 상태별 판단 일치 382/402(95%). 사기 정답이 있는 묶음 재현은 두 방식 모두 18/33, 정답 없는 묶음 Yes는 30 대 29, 정상 Yes 묶음은 4 대 7이다. F5는 묶음 쪽이 4/4로 줄마다(2/4)보다 높고, F4·F6은 1묶음씩 적다.
- 결정: 새 줄 전부를 한 번에 묻는다. 표본이 작아 큰 표본 평가에서 다시 본다.

### 상태 질문 6개를 한 질문으로 합칠지 (2026-11-22)

사용자가 상태 질문 6개를 한 번에 물을 수 있는지 물었다. 지금도 질문 6개를 한 요청에 담아 Jev를 1번 부른다. 질문 1개로 합치지 않고 지금 방식을 유지한다.

- [TypeSafe 문서](https://docs.typesafe.ai/primitives)에 따르면 한 요청의 질문은 같은 대화를 한 번 읽고 각각 따로, 동시에 판단한다. 질문 종류는 `noul`(Yes/No 확률), `choice`(하나 고르기), `score`, `box`뿐이고 여러 개를 고르는 종류는 없다. 가격은 입력 100만 토큰당 $0.042이고 출력은 무료다.
- 같은 창 3개로 쟀다. 질문 6개 한 요청은 입력 약 3.7k 토큰·0.2초, 질문 1개씩 6요청은 합계 약 6k 토큰이고 판단은 같았다. 입력 토큰은 대부분 질문마다 반복되는 공통 안내문이다(대사 5줄은 약 300토큰).
- 하나 고르기 질문(없음+F1~F6)으로 합치면 동시에 켜진 상태를 놓친다. 창 방식 측정에서 상태가 켜진 대사 중 2개 이상 켜진 비율은 사기 24%(121/494), 정상 2%였다. 보기 확률은 합이 1이라 기준값으로 여러 개를 고르는 방법도 맞지 않는다.
- 토큰을 줄이려면 공통 안내문을 줄일 수 있다. 요청 1건 약 $0.00016이라 급하지 않고, 문구를 바꾸면 다시 재야 한다.

버전별 변경 이유와 결과는 [Jev 상태 질문 버전별 변경 이력](../../../docs/analysis/jev-state-question-versions.md)에 모아 둔다.
