# 진행과 검증 기록

## 2026-11-15 설계 제안

- 경위
  - [KorCCVi 수법 분석](../../../docs/analysis/korccvi-scam-tactics.md)으로 R1~R9와 NEW 수법을 대화 특징 6개(F1~F6)로 다시 묶었다.
  - 사용자는 다음 방향을 제시했다.
    - 이 6개를 Jev가 판단하는 상태로 만든다.
    - 관찰·주의·경고 단계는 쓰지 않는다.
    - 켜진 상태에 맞는 에이전트를 부른다.
    - 대응은 전역 문구가 아니라 LLM이 지금 대화를 보고 최종 판단해 쓴다.
  - 이 방향에 다음 두 가지를 더해 [spec](spec.md)과 [design](design.md)에 제안으로 기록했다.
    - 절대선: LLM이 정상으로 판단할 수 없는 요구
    - 판단 근거 제한: 상대가 주장한 신분·절차는 근거로 쓰지 않는다
- 데이터 근거(KorCCVi 사기 694통화, 판단불가 제외, LLM 라벨, 사람 검수 없음)
  - 상태별 출현율(괄호는 첫 등장 상대 위치 중앙값)
    - F1 20.5% (0.28)
    - F2 35.6% (0.30)
    - F3 18.4% (0.53)
    - F4 78.1% (0.20)
    - F5 39.5% (0.37)
    - F6 83.4% (0.03)
  - 특징이 2개 이상인 통화는 608건(88%)이다.
  - 이 수치는 기존 라벨을 F 묶음에 다시 배정해 낸 것이다. 재배정 스크립트는 아직 저장소에 없고, 대화 중 임시로 실행했다.
- 아직 실행하지 않은 것
  - 코드 변경
  - Jev 실제 호출
  - 평가

## 2026-11-16 팀장 협의와 이슈 등록

- 사용자가 팀장과 이 구조로 전환하기로 협의했다. 상태별 LLM은 Claude API 에이전트로 쓰고, 판단 결과별 점수를 매긴다.
- F1은 복잡하지 않게 하기로 했다. LLM 호출 1번과 사기계좌 조회 tool 하나, 확인 질문 3개로 구성한다([design](design.md)의 F1 간단 구성).
- 작업 이슈 [#13](https://github.com/M4-Scamshield/scam-agent/issues/13)을 등록했다.
- 코드 변경, Jev 실제 호출, 평가는 아직 하지 않았다.

## 2026-11-16 미정 사항 결정

- 사용자가 [design](design.md#결정-사항-2026-11-16-사용자-결정)의 결정 사항을 정했다.
  - `voice_phishing` 질문은 당분간 남기되 나중에 없앤다. 없애는 근거를 얻으려고 평가에서 "이 질문만 Yes인 사기"를 따로 센다.
  - 상태 에이전트만 Claude API로 만든다. BE 계약은 바꾸지 않고 상태 결과를 `OBSERVE/WARN`과 score로 바꿔 내보낸다.
  - 점수는 임시 값으로 시작한다. tool은 F1·F3용 Mock만 만든다.
- 남은 미정: Jev 기준값, 실제 tool API, F2 기준표

## 2026-11-16 Jev 상태 질문 소량 실호출

- 스크립트: [probe_states.py](../../../experiments/jev_states/probe_states.py)
  - 질문: 공통 지시 + 상태별 Yes/No 기준, 그리고 기존 `voice_phishing`
  - 결과: [probe.json](../../../experiments/jev_states/results/probe.json). call_id, 정답, 판단·확률, 지연, 토큰만 있고 대본은 없다.
- 표본: KorCCVi 사기 15통화(판단불가 제외, 3,000자 이하, seed 0, F1·F2·F3·F5 양성 우선 포함)와 정상 5통화
  - 통화마다 전체 대본(화자 표시 줄 목록)을 1번 보냈다.
  - 정답은 LLM 라벨을 F로 다시 묶은 통화 단위 존재 여부다. 사람 검수는 하지 않았다.
- **형식 확인:** 질문 7개를 한 요청에 보내도 받는다. 20/20 성공, 실패 0이다. 각 답에 `choice`와 Yes/No 확률이 온다.
- **지연·토큰:** 지연 중앙값 0.23초, 최대 4.23초. 입력 토큰 중앙값 3,307, 합계 71,635. 출력 토큰 합계 4,160.
- **기본 판단(Yes) 결과** (사기 15통화 안에서 정답 대비, 정상은 5통화)

  | 질문 | 재현 | 사기 통화 오탐 | 정상 통화 Yes | P(Yes) 중앙값(정답 있음/없음) |
  |---|---:|---:|---:|---|
  | F1 | 2/3 | 0/12 | 1/5 | 0.98 / 0.00 |
  | F2 | 3/5 | 2/10 | 0/5 | 0.84 / 0.03 |
  | F3 | 3/3 | 1/12 | 2/5 | 0.85 / 0.05 |
  | F4 | 7/10 | 1/5 | 0/5 | 0.62 / 0.04 |
  | F5 | 2/7 | 0/8 | 0/5 | 0.14 / 0.00 |
  | F6 | 8/13 | 0/2 | 0/5 | 0.67 / 0.00 |
  | voice_phishing | 10/15 | — | 0/5 | 0.73 / 0.00 |

- **해석**
  - 사기 통화에서 F 중 하나라도 Yes인 통화는 13/15이고, `voice_phishing` Yes는 10/15였다. 작은 표본이지만 상태 질문이 더 많이 잡았다.
  - `voice_phishing`만 Yes인 통화는 0건이었다. 없앨 근거 쪽으로 기운다. 큰 표본에서 다시 센다.
  - 정상 2통화에서 F1·F3이 Yes였다. 상태는 사기 판정이 아니므로 설계대로 에이전트가 걸러야 할 경우다. 정상 통화의 종류는 이번에 확인하지 않았다.
  - F5(2/7)와 F6(8/13)가 약하다. 기준값을 0.1까지 낮춰도 F5 4/7, F6 9/13이다. 기준값보다 질문 문구 문제로 본다.
  - F2·F3은 기준값을 0.3으로 낮추면 오탐이 F2 5/15, F3 7/17로 빠르게 는다. 기준값은 상태마다 따로 정해야 한다.
  - 사기 2통화(4줄, 10줄)는 모든 질문이 No였다. 짧은 통화라 근거가 적었을 수 있다.
- **한계:** 20통화뿐이다. 통화 전체 대본을 한 번 보냈으므로 발화 시점별 감지와 지연은 재지 않았다. 정답은 사람 검수 전 LLM 라벨이다.
