# 변경 요구사항

상태: 확정(2026-11-22), 구현 중. 구현 방법은 [구현 계약](design.md#구현-계약-2026-11-22)에 있다.

## 상태 정의

| 상태 | Yes 기준 | No 기준 | 절대선 |
|---|---|---|---|
| F1 자산 넘기기 | 송금, 수수료·예치금·상환금 납부, 받은 돈 재전달·현금 전달, 통장·카드·비밀번호 양도 | 급여·환불·대출금을 받을 계좌번호만 물음 | 받은 돈 재전달·현금 전달, 통장·카드 양도, 수사·금융당국을 주장하며 송금 요구 |
| F2 정보 캐기 | 인증번호·OTP·비밀번호·카드번호, 잔액·계좌 수·거래 은행·자산 진술, 신분증 사본 | 이름·생년월일로 본인 확인만 함. 사건에 나온 계좌를 직접 만들었는지 추궁만 함(F4) | 인증번호·OTP·비밀번호·카드번호 |
| F3 통화 밖 이동 | 앱 설치, 링크·IP 주소 접속, 다른 번호·메신저, 은행·지점·만날 장소처럼 거래나 대면이 일어나는 곳으로 이동 | 공식 대표번호·공식 홈페이지 안내, 혼자 있는 곳·조용한 곳으로 옮기게 함(F5) | 통화 중 원격제어 앱 설치 |
| F4 공포·미끼 | 사건 연루·혐의 추궁·처벌·소환·동결 위협, 돈을 먼저 내는 조건의 혜택·고수익 약속 | 일반 상품 안내, 마감 일정 안내, 선입금 조건 없는 저금리·대출 제안 | — |
| F5 고립·의심 차단 | 비밀 유지·신고 금지, 주변을 피해 혼자 있게 함(녹취·통화 품질을 핑계로 제3자가 듣지 못하게 하는 경우 포함), 메신저·인터넷 등 다른 사람과의 연락을 막음, 통화 유지 강요, 은행원·가족·담당자에게 할 말 지시, 직접 확인을 막음("기록이 남지 않으니 확인할 필요 없다" 등) | 의심에 해명하거나 안심시키기만 함 | 은행원·가족에게 할 거짓말 대본 |
| F6 권위·절차 연출 | 수사·금융·공공기관명과 직함·이름으로 자기소개, 사건번호·공문·규정·녹취 절차 언급, 전화 조사·인물 확인, 대형 금융그룹·정부 지원 상품을 내세움 | 기관이나 회사를 내세우지 않음 | — |

F2·F4·F5의 No 경계는 v2 미탐·오탐 확인 뒤 2026-11-16 사용자 결정으로 정했다(v3). F5의 녹취 핑계 차단·연락 차단과 F3 장소 이동의 범위는 새 표본 확인 뒤 2026-11-17 사용자 결정으로 정했다(v4). 평가 정답에서 F5는 N7(안심·의심 무마)을 빼고 센다. F4는 N6(혜택 약속)을 같은 통화에 돈 요구(R1)가 있을 때만, N5는 혐의 추궁 라벨만 센다(2026-11-18 사용자 결정). F5·F6 정의는 같은 날 소량 실호출 v2에서 넓혔다. F6은 자기소개만 해도 Yes이므로 정상 금융 상담에서도 켜질 수 있다. F6은 보강 신호이고 판단은 에이전트가 한다. 근거: [버전별 변경 이력](../../../docs/analysis/jev-state-question-versions.md)

## 충족해야 할 동작

- 발화가 들어올 때마다 Jev에 최근 5줄(새 발화와 그 앞 4줄)을 보내고, 상태별 Yes/No 질문 6개로 마지막 대사에 그 행동이 나타났는지 묻는다. 앞 4줄은 대사를 이해하기 위한 맥락이다. 상태마다 Yes 확률을 State에 저장한다(2026-11-22 사용자 결정. 근거: [창 방식 비교](../../../docs/analysis/jev-state-question-versions.md#v5-후보--최근-5줄-창-2026-11-22)).
  - BE가 새 발화 여러 줄을 한 요청으로 보내면, 새 줄 전부와 그 앞 4줄을 한 번에 보내고 새 대사 중 어느 한 줄에라도 그 행동이 나타났는지 묻는다. Jev 호출은 요청마다 1번이다(2026-11-22 사용자 결정. 근거: [묶음 확인](../../../docs/analysis/jev-state-question-versions.md#v5-새-줄-묶음-확인-2026-11-22)). BE `agent-bridge`가 새 줄 전체를 넘기도록 바꾼다([구현 계약](design.md#구현-계약-2026-11-22)).
  - State의 대화 누적은 그대로 둔다. 상태별 LLM은 전체 대화를 받는다.
  - 기존 `voice_phishing` 질문은 뺀다(2026-11-22 사용자 결정). 창·묶음 방식 측정을 모두 이 질문 없이 했다.
  - Jev 호출 실패나 잘못된 출력은 오류로 처리한다. 모든 상태를 No로 바꾸지 않는다.
- 라우팅
  - 상태가 Yes이고 아직 처리하지 않았으면 해당 상태의 LLM을 부른다. 상태 하나만 켜져도 부른다.
  - 예외: 이 통화에서 지금까지 켜진 상태가 F3·F5뿐이면 LLM을 부르지 않고 기록만 남긴다. 다른 상태가 켜지면 그때 보류한 F3·F5의 LLM도 부른다(2026-11-19 사용자 결정. KorCCVi에서 F3·F5 단독 사기는 1%).
  - 이미 처리한 상태가 새 대사에서 다시 Yes가 되면, 이전 판단이 `risky`면 다시 부르지 않고 `uncertain`·`within_normal`이면 다시 부른다(2026-11-22 사용자 결정).
  - 그 밖에는 부르지 않는다.
- 여러 상태가 한 번에 켜지면 각 상태의 LLM을 따로 부른다. 응답은 F1 → F3 → F2 → F5 → F4 → F6 순서로 정리한다.
- 상태별 LLM이 받는 입력
  - 전체 대화
  - 상태 이름과 Jev 확률
  - 지금까지 저장된 통화 맥락: 주장하는 통화 목적, 상대가 내세운 신분
  - tool 결과
  - 다시 부를 때는 이전 판단, 이유, 근거 대사
- 상태별 LLM의 출력: `{state, judgment: "risky" | "within_normal" | "uncertain", reason, response, actions}`
  - `reason`은 대화 근거를 쓴다.
  - `response`는 지금 대화 상황에 맞춘 대응이다. 전역 문구가 아니다.
  - `actions`는 사용자에게 보여 줄 버튼과 후속 안내다.
- 판단 제한
  - 절대선에 해당하는 요구는 `within_normal`이 될 수 없다. LLM이 그렇게 답하면 `risky`로 고치고 기록한다.
  - LLM은 상대가 주장한 신분이나 절차("녹취 조사 중", "보안 절차")를 정상 판단의 근거로 쓰지 않는다. 돈과 정보가 어느 방향으로 가는지, 통화 목적에 꼭 필요한 요구인지로 판단한다.
- 상태별 LLM 호출이 실패하거나 출력이 잘못되면 그 상태만 판단하지 않은 것으로 두고 다음 Yes에서 다시 부른다. 요청 전체를 오류로 만들지 않는다(2026-11-22 사용자 결정).
- tool 결과는 위험을 높이는 근거로만 쓴다. `flagged`면 코드가 `risky`로 고정한다. 조회되지 않았다고 `within_normal`로 판단하지 않는다.
- tool(F1 사기계좌 조회, F3 URL·앱·번호 확인)은 이번에는 Mock이다. 결과는 `flagged` / `not_found` / `error`로 구분한다. tool에는 대화 원문을 보내지 않는다.
- 통화 상태와 점수(2026-11-22 사용자 결정. BE의 점수 기준 SUSPECT·WARN 두 단계를 대체한다)
  - 통화 상태는 상태별 판단 중 가장 나쁜 것으로 정한다. 점수로 정하지 않는다.
    - 위험: `risky`인 상태가 하나라도 있다. 알림을 띄운다.
    - 주의: `risky`는 없고 점수가 남은 `uncertain` 상태가 있다. 화면 표시만 한다.
    - 정상: 그 밖.
  - 점수는 이 통화에서 지금 사용자가 경계해야 하는 정도다. 통화마다 0에서 시작한다. 상태마다 점수 칸이 하나 있고, 점수는 6칸의 합이다(최대 100). 같은 판단을 여러 번 받아도 더하지 않는다.
    - `risky`: 그 판단의 점수로 고정한다. 다시 판단하지 않고 내리지 않는다.
    - `uncertain`: 그 판단의 점수에서 시작한다. 그 상태가 다시 Yes가 되지 않으면 1분마다 절반으로 줄이고, 5 미만이면 0으로 둔다.
    - `within_normal`: 0.
    - 다시 판단하면 그 칸을 새 판단의 점수로 바꾸고 감소를 처음부터 다시 잰다.
    - 시간은 발화 시각으로 잰다. KorCCVi 평가에서는 대사 시작 시각(`start`)을 쓴다. BE가 발화 시각을 보내기 전까지는 브리지가 요청을 받은 시각을 쓴다.
- BE에는 기존 형식으로 내보낸다. 위험이면 `action`은 `WARN`, 아니면 `OBSERVE`이고, `score`는 위 점수다. 위험이 아니면 점수를 39 이하로 보내 BE 점수 기준(40 이상 SUSPECT)으로 알림이 뜨지 않게 한다. Java는 바꾸지 않는다(2026-11-22 사용자 결정). 주의를 BE에 전하는 방법은 미정이다.
- F1 판단은 LLM 호출 1번으로 끝낸다. tool은 사기계좌 조회 하나만 쓰고, 계좌번호가 대화에 나왔을 때만 부른다.

## 검증 가능한 완료 조건

- 실제 Jev에 질문 6개를 담은 요청을 보내 상태별 응답 형식을 확인한다.
- API 없는 테스트로 다음을 확인한다.
  - 새로 켜진 상태와, 다시 Yes가 된 `uncertain`·`within_normal` 상태만 호출한다. `risky` 상태는 다시 호출하지 않는다.
  - 한 요청에 새 줄이 여러 개면 새 줄 전부와 앞 4줄을 한 번에 보내고, 질문에 새 대사 줄 수를 넣는다.
  - 절대선을 강제로 `risky`로 고친다.
  - 여러 상태의 응답이 우선순위대로 정리된다.
  - 점수가 상태별 칸의 합으로 계산된다. `risky`는 그대로 남고, `uncertain`은 1분마다 절반으로 준다. 같은 판단을 여러 번 받아도 점수가 더해지지 않는다.
  - 통화 상태(위험·주의·정상)가 상태별 판단으로 정해지고, BE 형식(`action`, `score`)으로 바뀐다.
  - Mock tool이 `flagged` / `not_found` / `error`를 구분해 반환하고, `not_found`가 `within_normal` 근거로 쓰이지 않는다.
  - Jev 실패는 오류로 끝난다.
- KorCCVi 사기 통화의 줄 단위 라벨로 상태별 재현율과 감지 지연(근거 줄부터 감지까지의 발화 수)을 잰다. 정상 통화에서는 상태별 오탐 비율을 잰다.
