## 재시도와 진행 전달

재시도는 동기 analyze 안에서 같은 입력의 복사본으로 수행한다. 시도 하나에 도구 왕복으로 모델 API를 최대 두 번 호출할 수 있어 재시도 횟수와 API 요청 수는 다르다. SDK 자동 재시도는 켜지 않는다.

콜백 방식은 기존 호출 형태를 유지하면서 진행 정보를 추가한다. 서버는 콜백에 요청 식별자를 붙여 이벤트를 저장·전송하고, 프론트는 분석 중/실패와 기존 위험을 함께 표시해야 한다. 이 저장소는 실제 HTTP/SSE 전송이나 화면을 구현하지 않는다. 콜백 실패는 분석의 실패나 모델 재시도가 되지 않는다.

동기 재시도 중 새 입력은 서버가 보관하고 방 단위로 직렬화한다. 이전 state를 중복 제출한 요청의 정확히 한 번 실행은 서버 책임이다. 소진한 실패는 저장하고 단순 후속 발화만으로 없애지 않는다. 수동 재분석은 원래 요청·버전과 결과 채택을 별도 설계해야 한다.

총 대기는 기존 BE HTTP 55초를 넘을 수 있다. BE 연결 시 HTTP timeout과 작업 임대 시간을 함께 조정해야 한다. 별도 백그라운드 큐는 이번에 추가하지 않았다.

## 근거 선택

최종 판단 입력은 전체 대화이며 결과에서 직접 근거와 보조 맥락을 선택한다. 모델은 대화상 줄 위치를 반환하고 서버는 원래 seq로 대응시킨다. 번호 없는 과거 이력에 대해 위치를 seq로 위조하지 않는다. risky에 직접 근거가 없거나 존재하지 않는 번호를 반환하면 재시도 대상이다.

원문에 실제 등장하는 값으로 실행한 flagged 조회는 마무리 모델의 timeout·인증·잘못된 출력에도 보존한다. 그 위치를 최종 근거에 반영한다. 단순 맞장구의 고정 목록은 코드에서도 직접 근거에서 제거하되 전체 대화에는 유지한다. 인용·부정 등은 프롬프트에 명시했으며 실제 모델의 의미상 정확성은 별도 평가가 필요하다.

## 선택과 한계

- 별도 analysis_status를 사용해 위험도와 장애를 구분했다. 실패를 uncertain 판단이나 정상으로 대체하지 않았다.
- 인증·설정·요청 거부는 즉시 실패한다. 일시 오류만 최대 3회 추가 재시도한다.
- 문자열 history는 state에 번호 대응이 있으면 유지한다. 그 대응이 없으면 구조화 이력이 필요하다.
- 실제 프론트·BE 수정, 무발화 중 별도 스케줄링, 기존 보류·고정·감쇠·혼합 URL 라우팅 개선은 이번 범위에서 제외했다.
