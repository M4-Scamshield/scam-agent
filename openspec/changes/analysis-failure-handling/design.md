# 분석 실패 대응 설계 초안

상태: 초안. 사용자의 화면 상태·최대 재시도 3회·전체 문맥 판단·근거 필터링 방향을 반영했다. 실행 코드는 아직 변경하지 않았다.

## 기존 구조와 변경할 부분

[통화 그래프](../../../scamshield/agents/call_agent.py)는 Jev 감지 → 상태별 Haiku 병렬 분석 → 점수·통화 상태 계산 순서다. [현재 계약](../../../docs/design/state-and-graph.md)은 일부 Haiku 실패를 생략하고 다음 Yes에서 다시 호출한다. [R1 분석](../../../docs/analysis/runtime-risk-review.md)에 이 정책의 정상 오인과 복구 누락을 재현했다.

후속 구현에서는 `judge_states`에서 실패를 명시적 결과로 수집하고, `finalize`가 위험 판단과 분석 완료 여부를 구분하는 방향을 검토한다. 저장할 복구 정보는 [AgentMemory와 AnalysisOutcome](../../../scamshield/state.py)의 호환성을 함께 다뤄야 한다.

## 책임·인터페이스·데이터 흐름 제안

- 공통 전송: 현재 오류 코드를 보존하고 원인별 진단 정보를 제공한다. 여기서 무조건 재시도해 전체 대기 시간을 늘리지 않는다.
- 상태 분석: 도구에서 확보한 위험 결과를 모델 마무리와 독립적으로 보존한다.
- 통화 그래프: 성공·실패를 구분해 수집하고 미완료 상태와 근거를 다음 요청에 넘긴다.
- 호출 서버: 원문·최신 state 저장과 재시도 실행을 연결한다. 새 발화가 없어도 실행할지, 별도 호출이 필요한지 계약을 정해야 한다.
- 응답 소비자: 분석 완료 여부와 임시 안내를 처리한다. 현재 BE가 받아들일 수 있는 필드·상태·메시지 범위를 확인한다.

이는 적용 후보이며 실제 필드명과 API는 아직 정하지 않았다. 공통 계약이 채택되면 docs/design의 기준 문서에 반영하고 이 문서에서는 이번 적용 방법만 남긴다.

## 사용자 후속 방향의 적용 초안

공통 방향은 [State·Graph 후속 계약](../../../docs/design/state-and-graph.md)에 둔다. 사용자 제안인 최대 3회 재시도는 최초 시도 외 추가 3회로 해석한다. 하나의 분석 시도가 도구 왕복을 포함하므로 모델 API 요청 수와 구분한다.

- 서버의 분석 작업이 최초 분석과 재시도의 진행 상태를 발행하고, 프론트는 해당 구간이 미완료인 동안 `분석 중`을 표시하는 구조를 제안한다. 최종 성공 시 결과를 반영하고 소진 시 `분석 실패`를 전달해야 한다. 정확한 전송 필드·이벤트·실행 주체는 미정이다.
- 위험 상태와 작업 진행 상태를 별도로 관리한다. 기존 위험을 화면에서 숨기거나 정상으로 내리지 않는다.
- 재시도 입력은 실패한 분석의 전체 대화·감지 후보·원래 근거 후보·기존 판단을 식별할 수 있게 보관한다. 우선 같은 입력 버전으로 실패한 Haiku 상태 분석을 재실행하는 방안을 제안한다. 매번 성공한 상태·Jev·URL 조회까지 모두 반복할 필요는 없다. Jev 자체 실패의 재시도 범위는 별도로 정한다.
- 재시도 동안 도착한 새 발화는 잃지 않고 별도 구간으로 식별한다. 최신 맥락을 재시도에 합칠지와 오래된 결과의 반영 규칙을 정해야 한다. 새 발화·중복 요청으로 같은 실패 작업의 예산을 무한 초기화하지 않는다.
- 인증·설정 오류도 3회를 모두 시도할지, 즉시 실패로 종료할지는 아직 미정이다. 현재 오류 분류와 사용자 화면 정책을 함께 정한다.

## 문제 발화 선택의 현재 한계와 개선 초안

현재 Jev는 최근 4줄과 새 줄에서 행동 유형의 존재를 반환하며, 어떤 한 줄이 그 행동인지 반환하지 않는다. 통화 그래프는 해당 묶음의 새 seq 전체를 `todo.seqs`에 넣는다. Haiku는 전체 대화를 읽고 판단·이유를 내지만 최종 근거 번호를 반환하지 않는다. 결과의 `evidence_seqs`는 따라서 실제 선택한 발화 목록이 아니라 위험 판단 요청에 포함된 새 줄 목록이다.

예를 들어 같은 묶음의 101번 기관 소개, 102번 “네”, 103번 송금 요구에서 F1이 risky이면 현재 근거는 `[101, 102, 103]`이다. 이 동작을 대역으로 확인했다. “네” 같은 짧은 응답도 문맥상 의미가 있을 수 있으므로 분석 입력에서 일괄 삭제하지 않는다. 최종 근거는 요구와 그 요구를 해석하는 맥락을 구분해 선택해야 한다.

개선 후보는 다음과 같다.

1. 전체 대화를 최종 판단 입력으로 유지한다. 후보 감지 창의 유지·변경과 맥락 변화 시 재평가 정책은 별도 결정한다.
2. 상태별 분석 출력에 직접 요구와 보조 맥락의 근거 번호를 받는 방법을 검토한다. 실제 위험 발화의 번호·내용·화자와 판단 이유를 대응시킨다.
3. 서버에서 실제 입력에 있는 번호인지 검사한다. 모델이 임의 번호를 만들거나 후보 전체를 근거로 복사한 결과를 자동 승인하지 않는다. 의미상 적합성·인용·부정 처리는 별도 검증 사례로 확인한다.
4. 번호 없는 `history: list[str]`만으로 이전 발화의 원래 seq를 복원할 수 없다. 구조화된 이력 또는 별도 번호 대응을 검토하고 BE·기존 호출자와 호환 방법을 정한다.
5. 실패 재시도 대상은 최종 위험 근거만으로 결정하지 않는다. 분석이 실패하면 그 근거가 아직 없을 수 있으므로 실패 작업의 원래 후보와 전체 맥락을 보존한다.

최종 근거가 잘못되거나 비어 있을 때 모델 결과를 거부·재시도할지, 도구 근거가 있는 경우 어떻게 보완할지는 미정이다. 근거 선택 기능을 구현 완료로 간주하지 않는다.

## 선택·대안·trade-off

| 후보 | 장점 | 한계·확인할 점 |
|---|---|---|
| 상태별 분석 완료 여부를 별도 표현 | 위험도와 장애를 섞지 않음 | BE·UI가 새 정보를 소비해야 함 |
| 기존 주의 상태로 임시 표현 | 기존 상태 집합을 활용할 여지 | uncertain 판단과 장애의 의미가 섞임, 사유 구분 필요 |
| 즉시 제한적으로 재시도 | 일시 장애를 같은 요청에서 복구할 수 있음 | 경고 지연·중복 부하·상위 timeout 초과 가능 |
| 미완료 작업을 보관해 후속 실행 | 성공 결과를 빨리 전달하고 복구 가능 | 실행 주체·순서·중복 방지·원문 보존 계약 필요 |
| timeout 연장 | 느린 응답 일부를 받을 가능성 | 출력 오류·연결·429는 해결하지 못하고 대기가 길어짐 |

## 미정 사항과 검증 방법

1. 분석 완료 여부의 출력·저장 schema, 기존 state 마이그레이션과 소비자 호환성.
2. `분석 중`·`분석 실패`의 구간별 전송과 화면 표시, 기존 위험 안내와의 병행, 이후 새 분석이 성공할 때 과거 실패 구간 표시.
3. 최대 3회 재시도의 상태별·단계별 적용, 간격·총 시간·오류별 예외와 실행 주체.
4. 같은 입력 버전 재시도와 최신 대화 반영, 통화 종료·오래된 작업·중복 요청 처리.
5. 근거 선택 출력·원래 seq 보존·근거 검증 실패 처리와 후보 감지 누락 시 재평가 정책.
6. 실제 지연·오류 계측 위치. 현재 로그는 상태와 오류 코드 위주라 timeout의 실측 원인을 알 수 없다.

검증은 [요구 초안](spec.md)의 실패 주입·근거 보존·복구·호환성 조건으로 한다. 대기 한도를 숫자로 정하기 전에는 현재 API·서버 timeout과 호출 경로를 확인한다.
